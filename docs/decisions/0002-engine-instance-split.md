# 0002. Split engine and instance repositories

* Status: proposed
* Date: 2026-04-24
* Deciders: venil
* Tags: architecture, deployment, repository, open-source

Historical ADR translated from the [original Russian record](https://github.com/Lenivvenil/digest/blob/0b939fb6b065723eee278069fec546980788e439/docs/decisions/0002-engine-instance-split.md). Status, claims and references are preserved as recorded.

## Context and Problem Statement

The `digest` project has reached v2.0.0 and is running as a live product. The repository contains the engine source code, private configuration with RSS sources and a Telegram chat ID, and runtime artifacts (`.cache/`, `digests/`) that GitHub Actions commits back after every run. ADR-0001 explicitly assigned this split to ADR-0002. The pipeline is fixed (PR #33) and governance is installed: this is the first clear window for a topology decision without risking production.

## Decision Drivers

* Making the engine public without disclosing private RSS sources and the Telegram chat ID is currently impossible: the config is physically in the same repository
* Private config should not live in the same repository as public code; they are together by structure, not by mistake
* The development git log is polluted by autogenerated `digest:`/`discover:` pushes; diagnosing regressions requires visually separating data from code
* The 19 April failure remained invisible until a deliberate investigation; with a split, the data repository either becomes empty (immediately visible) or fails in isolation
* Rule 4 in claude-mini governance conflicts with data pushes to main; a regex carve-out is fragile, while a separate repository resolves this structurally

## Considered Options

* **A. Orphan branch `content`** — `digests/` and `.cache/` are committed to a separate branch in the same repository; `main` contains only code and config
* **B. Two repositories: engine + instance** — `digest` becomes a candidate for publication (code, tests, CI); `digest-prod` is a private repository with `config.yaml`, `.cache/`, `digests/`, workflows and secrets
* **C. Git submodule** — `digest-prod` contains the engine as a submodule, which the production workflow clones recursively
* **D. Pip package from a git tag, without a new repository** — the engine is published as an installable package; the production workflow stays in the existing private host repository
* **E. Monorepo with branch protection** — the workflow isolates data commits in a separate `state` branch; `main` is PR-only

### Option A — Pros and Cons

Good:
* One repository, one set of secrets: minimal operational complexity
* A clean `main` log without data commits
* Reverting a digest commit does not touch code (reset the `content` branch, not `main`)

Bad:
* A repository cannot be partially public: either the whole repository is open (including `main` with the source list) or it is private
* Config.yaml with private sources stays in `main`; drivers #1 and #2 remain unmet
* Obsidian git-sync becomes more complicated: the client needs a separate branch checkout
* An orphan branch is an unusual pattern, making CI harder to configure

### Option B — Pros and Cons

Good:
* Complete isolation of public code from private config: both drivers #1 and #2 are met structurally
* Rule 4 is resolved without a carve-out: the engine receives no data commits at all
* A viable open-source path: publish the engine with an example config; keep the instance private
* Failures can be attributed to the engine (code bug) or the instance (secrets, cron, network): two distinct contexts

Bad:
* Two repositories mean two sets of secrets and two places for troubleshooting and monitoring
* A release contract is needed between engine and instance: a public API change is a breaking change; without semver discipline, the instance breaks on the next cron run
* Bootstrap cost: rename the package from `src/` to `digest/`, move `config.yaml` / `.cache/` / `digests/` / workflows, and create a new repository

### Option C — Pros and Cons

Good:
* The production repository gets the engine as-is without packaging
* A pinned SHA makes reproducibility deterministic

Bad:
* The submodule workflow is unintuitive: `git submodule update --init` after every pull, and an extra CI step
* It does not provide privacy: the submodule reference in git config exposes the engine repository URL to everyone with instance access
* Bumping the engine version requires a manual commit in the instance to update the SHA: an implicit release contract without semver

### Option D — Pros and Cons

Good:
* No new repository, so operational complexity does not increase
* `pip install git+https://...@v2.1.0` in the existing host repository is a standard mechanism

Bad:
* Config.yaml and the source list stay in the same repository as the code; privacy remains unresolved
* Requires an existing private host repository with a configured token; without one, it effectively becomes Option B with an extra step
* The engine repository contains `digests/` and `.cache/` in git history; `pip install` pulls the entire tree, bloating the package

### Option E — Pros and Cons

Good:
* One repository, no extra operations
* `main` is PR-only with branch protection configured

Bad:
* Config.yaml with private sources stays in `main`; drivers #1 and #2 remain unmet
* Branch protection + GHA writes require finely tuned `contents: write` permission: a fragile setup
* Rule 4 still requires a bot-author carve-out; this does not resolve it structurally
* The path to publication is blocked: the history of `main` contains config in earlier commits

## Decision Outcome

Chosen option: **Option B — Two repositories: engine + instance**

Only B meets both driver #1 (publication without disclosure) and driver #2 (physical separation of private config from public code). The other options:
* **A, C, E** — do not resolve privacy; drivers #1 and #2 remain unmet
* **D** — resolves it partially, but requires an existing host repository and leaves data artifacts in engine history

Governance rule 4 (driver #5) is resolved structurally without a carve-out: the engine repository receives no `digest:`/`discover:` commits, and the instance follows its own rules.

Acknowledged costs: two sets of secrets, a release contract with semver discipline, and migration bootstrap costs.

### Positive Consequences

* The engine can be made public with an example config: a viable open-source path
* From the split onward, `digest` (engine) history contains only feat/fix/chore/adr; `git log` can be read without filtering
* Code regressions are isolated from production incidents: two issue trackers, two contexts, no attribution confusion
* Dogfooding: another user of the engine as a pip dependency validates the public API; the API is currently coupled to one instance by accident
* Dependabot on the engine becomes a meaningful public PR stream, separate from data commits

### Reversibility

The decision is **partially reversible**, but with a nonzero minimum cost. Returning to a monorepo requires merging the two repositories' git histories (either losing instance history or using `git replace`), moving `config.yaml` / `.cache/` / `digests/` back into `digest`, rebuilding workflows, rotating or combining the two sets of secrets, and, if the engine was public, deciding whether to make it private (which does not erase already indexed forks and clones). Estimated rollback effort after 6–12 months: 1–2 working days. If the split has existed for less than 3 months and the instance repository has not accumulated significant history, rollback is closer to 2–4 hours.

### Negative Consequences

* Two repositories mean two places for monitoring, secrets rotation and troubleshooting
* A release contract is mandatory: a public API change in the engine without a bump in the instance causes silent breakage on the next cron run; semver discipline is required
* Bootstrap cost: rename the package from `src/` to `digest/`, create `digest-prod`, and move `config.yaml` / `.cache/` / `digests/` / workflows
* Debugging spans repositories: a bug reproducible only in production needs two checkouts + `pip install -e engine`, instead of `cd ~/code/digest && pytest`
* The security surface doubles when the engine is published: outsiders can analyze SSRF in the feed parser, dependency confusion and supply chain issues; publication explicitly accepts this surface
* Issue triage is spread across repositories: a production incident first requires attribution, "engine or instance?", before investigation starts
* Actual publication incurs an open-source tax: external PRs and issues put pressure on documentation and backward compatibility
* The Dependabot workflow gets longer: merge in engine → tag release → bump pin in instance = +15 minutes per update instead of one operation
* Claude Code context is spread across repositories: work in the engine cannot see the instance config, and vice versa; MCP/Serena indexes must cover both repositories

## Confirmation

Four specific checks:

1. **Weekly (during `/project-health`):** engine main contains no `digest: YYYY-MM-DD` or `discover: YYYY-MM-DD` commits from the past 7 days. Threshold: **any such commit = a data leak into the engine; investigate immediately**.

2. **For every dependabot bump:** no more than 72 hours pass between the engine merge and the corresponding bump PR in the instance. Measure with `gh pr list`. Threshold: **more than 2 consecutive breaches = the release contract is not working; revisit**.

3. **Monthly:** `grep -r "TELEGRAM\|API_KEY\|feeds:" engine-repo/` returns only example/placeholder values. Threshold: **any real secret or private feed URL = a critical leak**.

4. **After every production failure:** attribution time ("engine or instance?") is ≤5 minutes using the GitHub Actions log. Regularly exceeding this means issue triage is more fragmented than expected.

## Re-visit Trigger

1. **Within 6 months of the split, the engine has received no external contributors, issues or dependabot PRs beyond what the monorepo would have received.** The "publication" driver was theoretical; the overhead of two repositories does not pay off. Roll back or switch to D.

2. **The release contract is breached three times in a row within a quarter:** the instance breaks on cron after an engine bump without warning. Semver discipline is not sustainable for one developer; a CI gate is needed (an engine compatibility test runs the instance), or a return to a monorepo.

3. **Anthropic or the community releases an official toolkit for personal agent pipelines** that assumes a different repository topology. The current split architecture becomes an idiosyncrasy.

4. **Migration from the Mac mini to another platform:** the infrastructure baseline changes, requiring reassessment of all architectural decisions.

**Not triggers (noise vs signal):**
* Individual failed Actions runs in production — operational noise
* Occasional inconvenience from having to clone two repositories — acknowledged cost
* One dependabot PR taking longer than 72 hours to merge — noise; the trigger requires a pattern
